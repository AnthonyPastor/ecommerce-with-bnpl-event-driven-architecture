# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this service is

`api-gateway` is the single entry point the `frontend/` talks to (`http://localhost:3000/api/...`). It does three things and nothing else: injects/propagates `x-correlation-id`, verifies JWTs at the edge (so downstream services don't each reimplement auth), and reverse-proxies to the right backend service. It has no database and no business logic.

**Payment gateway webhooks bypass this service entirely** — they hit `payment-service` directly (see that service's CLAUDE.md), since they need a stable public URL and must not require a JWT.

## Commands

Run from `backend/` (the pnpm workspace root):

```bash
pnpm install                          # once
pnpm --filter api-gateway start:dev   # dev server, port 3000 by default
pnpm --filter api-gateway build
pnpm --filter api-gateway test        # unit tests (the auth middleware logic)
```

There is no e2e suite here by design — proxying correctness is exercised by `backend/e2e/` against the real stack, since a gateway-only e2e would just be re-testing `http-proxy-middleware`.

## Architecture

### A NestJS controller per proxied mount, backed by one shared ProxyService

Each backend service gets its own `@Controller()`, each with a single `@All(['/', '*'])` handler that calls `ProxyService.forward(req, res, { target, stripPrefix })` (`src/proxy/proxy.service.ts`). The five mounts that are a pure `strip /api, forward, done` passthrough (`cart`, `orders`, `payments`, `notifications`, `installment-plans`) are generated by `createProxyController(routePrefix, envVar, defaultTarget)` (`src/proxy/create-proxy-controller.ts`) — their `*.controller.ts` files are just one-line calls into it. `catalog.controller.ts` and `auth.controller.ts` are hand-written instead because they need per-route `@Public()` or a different `stripPrefix`. If you need a new pure-passthrough proxy, add a `createProxyController(...)` call + module following one of the five, and register the module in `app.module.ts`; only reach for a hand-written controller (or extend the factory) if the new mount needs something the factory doesn't support.

### Auth-at-the-edge, not per-service

`GatewayAuthGuard` (`src/common/gateway-auth.guard.ts`) is registered globally (`APP_GUARD` in `app.module.ts`) — every route requires a valid bearer token (verified with the shared `JWT_ACCESS_SECRET` from `auth-service`) unless its controller/handler is marked `@Public()` (`src/common/public.decorator.ts`). On success it injects `x-user-id` into the proxied request headers, so downstream services can trust that header instead of re-verifying — `payment-service`'s `GET /payments?orderId=` does exactly this to scope results to the caller (see that service's CLAUDE.md); any new endpoint that returns per-user data should do the same rather than trusting a client-supplied id. `catalog.controller.ts` is `@Public()` at the class level (browsing needs no auth); `auth.controller.ts`'s register/login/refresh handlers are `@Public()` individually since other routes on that same controller (e.g. `/auth/me`) still require a token. Every other controller (`cart`, `orders`, `payments`, `installment-plans`, `notifications`) has no `@Public()` anywhere, so the global guard applies unmodified.

### No global body parser — proxied bodies stream through untouched

`main.ts` creates the Nest app with `bodyParser: false`. No controller here ever reads `@Body()` (every route is a pure proxy — see above), so Nest's default `express.json()`/`urlencoded()` middleware would only buffer and `JSON.parse()` every proxied request body for nothing, forcing `ProxyService` to re-serialize it right back with `fixRequestBody` before forwarding. With it disabled, `http-proxy-middleware` streams the raw request bytes straight to the target, same as the original raw-Express setup this NestJS-controller-based proxy replaced. If a future route on this service ever needs a parsed body (e.g. a real `@Body()` DTO), apply a body-parser middleware scoped to that one route only — don't re-enable it globally.

### Path rewriting depends on whether the target service uses its own prefix

`auth-service` exposes routes under `/auth/...` itself, so its proxy only strips `/api`. `catalog-service` exposes routes "naked" (`/products`, not `/catalog/products`), so its proxy strips `/api/catalog` entirely. `cart-service`/`order-service`/`payment-service`/`bnpl-service`/`notification-service` all expose routes matching their mount segment (`/cart/...`, `/orders/...`, etc.), so they follow the `auth-service` pattern (strip `/api` only). Check the target service's own controller `@Controller()` prefix before assuming which rewrite rule a new proxy needs.
